# Portside 0.16 Release Readiness and Product Benchmark

**Audit date:** 2026-07-26  
**Audited checkout:** `feature/fleet-inventory` at `57817ef`, including the
uncommitted and untracked 0.16 working tree  
**Auditor:** Codex CLI  
**Recommendation:** **Do not ship the current working tree.**

## Executive summary

Portside has a credible product thesis and a stronger implementation than its
version number suggests. The app builds cleanly, its existing test suite is
substantial, the packaged application is compact, and delegating transport to
the system OpenSSH client is an excellent architectural choice.

The current 0.16 working tree is not ready to release, however. There are three
release-critical implementation defects:

1. The release script can publish binaries built from a dirty feature checkout
   under a tag created from a different commit on GitHub.
2. The new history migration can overwrite existing workspace, shortcut, and
   credential-profile configuration with defaults.
3. Disabling the full connection log does not actually remove the persisted
   records, despite the UI promising that it does.

The planned 0.16 scope is also only partially represented in the current tree.
The connection log is collected but not browsable, recently closed tabs are
retained but have no browser, connection outcomes are not modeled, the visual
pass has not landed, and release documentation still presents the features as
future work.

The right competitive position is not "another SSH terminal." Portside is most
defensible as:

> A native, local-first Mac operations cockpit for large SSH fleets, built on
> the operator's existing OpenSSH configuration, with deliberate safety
> guardrails and a direct MobaXterm migration path.

A clean coverage build exposed warnings hidden during the normal incremental

The packaged application binary is **arm64-only**. Public documentation says
only that Portside requires macOS 14+, which includes Intel Macs capable of
running Sonoma.

A universal build attempt using:

```sh

```

failed because the Xcode Metal toolchain component is not installed. Portside
should either:

- explicitly state that releases require Apple silicon, or
- make universal packaging and architecture verification a tested part of the
  release pipeline.

## Release blockers

### P0-1: Release artifacts can differ from tagged source

**Files:** `Scripts/release.sh`, `Scripts/make_app.sh`

`release.sh`:

- derives the build number from committed `HEAD`
- builds whatever source is present in the local filesystem, including
  uncommitted and untracked files
- does not require the expected branch
- does not require a clean tree
- does not verify that local `HEAD` equals the target remote commit
- runs no tests before publishing
- calls `gh release create` without explicitly binding the release to the
  audited local commit

On the audited checkout, this creates a concrete failure mode: a binary
containing dirty 0.16 feature-branch changes could be published under a tag
pointing at `origin/main`/0.15 source.

The release script also treats Developer ID signing and notarization as
optional. If `PORTSIDE_SIGN_IDENTITY` and `PORTSIDE_NOTARY_PROFILE` are absent,
it still builds an ad-hoc-signed artifact and proceeds to publish it.

**Required remediation:**

- Fail if the tree is dirty or contains untracked source files.
- Require the expected release branch.
- Fetch and verify local `HEAD` equals its intended remote commit.
- Require the version to match a changelog entry.
- Run the complete test suite before packaging.
- Require Developer ID identity and notary profile for a public release.
- Verify the final app with `codesign`, `spctl`, and `stapler`.
- Create or verify the tag at the exact audited commit.
- Verify the release asset's embedded version and architecture.
- Consider producing a build manifest containing the commit SHA and asset
  hashes.

### P0-2: History migration can overwrite loaded configuration

**File:** `Sources/Portside/Services/SessionStore.swift`

`load()` assigns entries, macros, forwards, recents, appearance, defaults,
logging, terminal settings, and history settings, then calls:

```swift
loadHistory(migratingFrom: doc)
```

Only after that call does it assign:

- `workspace`
- `keyBindings`
- `credentialProfiles`
- `defaultProfileID`

When legacy history exists and the sidecar does not, `loadHistory` calls
`saveHistory()` followed immediately by `save()`. That `save()` serializes the
still-default values for the four properties above over the user's library.

The existing migration test checks only that command history and aggregate
statistics survive. It does not seed and assert preservation of workspace,
keybindings, credential profiles, default profile selection, custom themes,
forwards, and other fields.

**Required remediation:**

- Fully hydrate the document before performing any migration write.
- Better: have `loadHistory` return whether migration is required, then write
  only after `load()` has completed.
- Add a real v0.15 fixture containing every persisted field.
- Assert byte-level or semantic preservation of all unrelated fields.
- Back up the old library before a schema-changing migration.

### P0-3: Full-log opt-out leaves records on disk

**File:** `Sources/Portside/Services/SessionStore.swift`

In `updateHistorySettings`:

1. The new setting is assigned.
2. `saveHistory()` is called.
3. `connectionLog` is cleared in memory.
4. Only the main library is saved.

Therefore the sidecar retains the old connection log. The data returns on the
next launch, contrary to the UI text:

> turning it back off deletes what was collected

The command-history branch clears before saving and works correctly; the
connection-log branch has the operations reversed.

**Required remediation:**

- Clear both collections before `saveHistory()`.
- Add a test that enables the full log, records entries, disables it, reloads
  the store, and asserts that the persisted log is empty.

## High-priority correctness and security findings

### P1-1: Failed connection attempts are recorded as successful connections

**Files:** `SessionManager.swift`, `PortsideApp.swift`, `SessionStore.swift`

`SessionManager.postConnect` calls `onConnect?(entry)` immediately after the
child transport is created. It does not wait for:

- SSH authentication
- a remote shell
- serial open success
- telnet connection success
- mosh bootstrap completion

As a result, a failed connection:

- increments the host's count
- becomes the latest successful-looking activity
- affects Quick Connect frecency
- prevents the host from becoming stale
- appears in the optional full log

The 0.16 plan called for a timestamp and outcome, but `ConnectionLogEntry` has
no outcome field.

**Recommended design:**

- Record an attempt separately.
- Promote it to `connected` when the transport provides positive evidence.
- Record a failure outcome when the process exits before connection.
- Track at least `attempted`, `connected`, `authFailed`, `hostKeyFailed`,
  `timeout`, and `transportFailed`, with a tolerant unknown fallback.
- Use successful connections, not attempts, for last-connected and frecency.

### P1-2: Quick Connect loses legacy recency after the first new statistic

**File:** `Sources/Portside/Views/QuickConnectView.swift`

An empty query chooses either:

- new frecency results, or
- the legacy recents list when there are no statistics

It does not merge them. After upgrading, existing users have up to 20 recents
but no aggregate statistics. Their first new connection creates one stat, at
which point that one host is shown first and all other previously recent hosts
drop into the alphabetical remainder.

**Remediation:**

- Merge ranked aggregate results with legacy recents, deduplicating IDs.
- Migrate existing recents into initial statistics with count 1 and the
  recorded timestamp.

### P1-3: Transcript offsets are racy and usually stale

**Files:** `SessionManager.swift`, `SessionLogger.swift`

`LoggingTerminalView.dataReceived` calls `logger.append(slice)`. `append`
dispatches the actual stripping and write asynchronously to the logger's
private queue. `dataReceived` then immediately reads `logger.bytesWritten`.

`bytesWritten` is mutated on the private queue and read from another execution
context without synchronization. Even ignoring the data race, the newly
received chunk normally has not been written when the offset is captured.

Consequences:

- Command-history transcript links can point to earlier output.
- Heavy output makes the error grow.
- Swift 6 strict concurrency is likely to reject a properly annotated version.

**Remediation:**

- Move offset assignment onto the logger queue.
- Have `append` return or asynchronously report the resulting byte range.
- Alternatively, record the pre-write offset and map parser markers to offsets
  within the cleaned output chunk.
- Add a high-volume test that proves offsets land around the intended command.

### P1-4: Corrupt libraries are silently replaced

**File:** `Sources/Portside/Services/SessionStore.swift`

If `portside.json` exists but cannot decode, `load()` takes the same branch as a
first launch: it seeds from `~/.ssh/config` and saves. This can overwrite a
corrupt, hand-edited, partially migrated, or forward-incompatible library
without showing the user an error.

Atomic writes reduce the chance of partial files but do not protect against
schema bugs, disk damage, or manual edits.

**Remediation:**

- Distinguish "file missing" from "file exists but failed to decode."
- Never overwrite an undecodable library.
- Preserve a timestamped copy and show a recovery dialog.
- Include the decoding error and offer export/reveal/reset choices.
- Apply the same principle to the new history sidecar, which currently ignores
  decoding failures and silently falls back.

### P1-5: Credential-profile passwords are ignored by standalone tunnels

**File:** `Sources/Portside/Services/TunnelManager.swift`

Normal sessions resolve password precedence as:

1. assigned credential profile
2. host-specific password
3. default credential profile
4. legacy default password

`TunnelManager.start` checks only:

```swift
CredentialStore.password(for: entry.id)
```

A tunnel started without an existing ControlMaster connection therefore fails
when the host relies on an assigned/default profile password. This is especially
likely for auto-start tunnels.

**Remediation:**

- Centralize credential resolution in one service used by sessions, tunnels,
  mosh bootstrap, and any future helper.
- Test host, assigned-profile, default-profile, and no-password cases.

### P1-6: Kubernetes inventory metadata is interpolated into a shell command

**File:** `Sources/Portside/Services/ContainerLister.swift`

Kubernetes context and namespace are concatenated into a string:

```text
kubectl --context <value> -n <value> get pods --no-headers
```

For local targets the string is passed to the user's shell with `-lc`. For
remote targets it is passed as an SSH remote command and interpreted by the
remote login shell.

Because Portside supports importing portable JSON, a crafted library can place
shell metacharacters in these fields and cause code execution when the user
browses pods.

**Remediation:**

- For local execution, invoke `kubectl` directly with a process argument array.
- For remote execution, use a rigorously tested POSIX argument encoder or send
  a small fixed script with parameters over stdin.
- Validate imported context, namespace, pod, container, and shell values.
- Add hostile-value tests containing spaces, quotes, semicolons, newlines,
  substitutions, and leading dashes.

### P1-7: Release architecture is narrower than advertised

**Files:** `Scripts/make_app.sh`, README

The current build script emits only the host architecture. On the audited Mac,
that is arm64. No website or README language says "Apple silicon required."

Either support Intel explicitly with universal artifacts or make the platform
restriction explicit in:

- README
- website
- GitHub release notes
- Homebrew cask
- application download naming

## Incomplete or misleading 0.16 behavior

### Connection log is collected but not browsable

`HistoryView` renders one row per `ConnectionStat`, showing the latest date and
count. It never reads `connectionLog`. Users can enable a privacy-sensitive
full event log, accumulate thousands of timestamped records, and receive no
product value from it.

Ship one of:

- an event timeline with filtering, outcome, and host detail, or
- no full-log toggle until the browser exists.

### Recently closed tabs are retained but not browsable

`SessionManager` stores ten `RestorePlan.TabPlan` values but exposes only
`reopenLastClosedTab()`. This is still single-step browser behavior, not the
planned "browse any of the last N closed layouts."

### Visual phase is absent

The fleet-and-finish plan includes an app-level light/dark/system appearance and
a broader density, empty-state, sidebar, tab-strip, and iconography pass. The
audited working tree does not contain that phase.

### Release documentation is stale

- `CHANGELOG.md` has no 0.16 entry.
- README lists the 0.16 features under "Next up."
- README says OSC 133 remains blocked upstream even though the current code now
  parses OSC 133 itself.
- `docs/COMPATIBILITY.md` was last verified against 0.6.1-dev.
- Current SwiftTerm source contains Sixel, Kitty, and iTerm2 image-protocol
  implementations, so the old assertion that all are upstream limitations must
  be re-tested rather than repeated.

## Privacy and security notes

### Protected-host exclusion is prospective, but its wording sounds absolute

Turning on "Exclude protected hosts entirely" prevents future:

- recents
- aggregate stats
- full-log events
- command records
- transcripts for newly opened sessions

It does not remove existing history, commands, recents, or transcript files.
Already-open sessions also retain the recording configuration they had when
created.

The UI should either:

- offer to purge existing protected-host records and identifiable transcripts,
  or
- state clearly that the setting applies only to new sessions/activity.

### Security documentation is inaccurate

`SECURITY.md` currently says:

- passwords and passphrases are stored in Keychain and "never on disk"
- plain JSON contains no secrets

The implementation intentionally writes saved credentials into a private
temporary askpass file for up to roughly 30 seconds. This is reasonably
hardened:

- unique per-connection directory
- directory mode 0700
- secret file created atomically as 0600
- no secret in process arguments
- supplied only once
- early expiration and final cleanup

But "never on disk" is not technically true. The document should say passwords
are never persisted in the library and are staged briefly in a private
single-use askpass file.

Opt-in command history is JSON and can contain passwords, API tokens, private
keys, headers, and environment assignments typed inline. The UI warns about
this well, but `SECURITY.md` must acknowledge it.

### File permissions

Observed files were mode 0644:

- `portside.json`
- `portside.history.json`
- session transcripts
- manual backup copies

On the audited machine, the parent `~/Library` and Application Support
directories are mode 0700, which mitigates cross-user access. Still, sensitive
history and transcripts should be explicitly created as 0600 so their security
does not depend on parent-directory conventions or later relocation.

### Predictable ControlMaster directory

`SSHControl.controlDir` is the fixed path `/tmp/portside-ssh`. Portside attempts
to create it as 0700 but does not validate an existing path's type, ownership,
or permissions.

Use a per-user directory under `FileManager.default.temporaryDirectory` or
Application Support, verify ownership and mode, and reject symlinks or
unexpected pre-existing paths.

### SFTP batch quoting

SFTP paths escape backslashes and double quotes, but not embedded newlines.
Unusual local or remote filenames can inject additional SFTP batch commands.
This does not directly become shell code, but it can cause unintended remote
file operations.

Add newline/control-character handling and tests for adversarial filenames.

### Shell integration side effects

Command history currently supports bash and zsh only. The bash integration:

- installs a DEBUG trap, potentially replacing a user's existing trap
- treats `PROMPT_COMMAND` as a scalar, while modern bash also permits arrays
- captures the first simple command rather than necessarily reconstructing the
  exact interactive compound command

Parser tests are strong, but there is no end-to-end test that starts real bash
and zsh instances with the installed snippet and verifies emitted markers,
trap coexistence, command text, and exit codes.

### Terminal-output trust

OSC 133 records are accepted from the raw terminal stream. A remote host or
program can emit spoofed markers and create arbitrary command-history entries.
This is not local code execution, but the history UI should not treat the stream
as cryptographically authoritative. It is shell-reported metadata.

## Inventory coverage product review

The inventory-coverage concept is the most differentiated part of 0.16, but
the current completeness score conflates facts with one particular credential
policy.

### Every host without a shared profile is considered incomplete

`noCredentialProfile` matches every host that lacks a live shared profile,
including hosts with:

- a valid unique key
- a host-specific Keychain password
- SSH-agent authentication
- a complete `~/.ssh/config` rule
- certificate or smart-card authentication

Because `coveredFraction` includes this gap, such users can never reach 100%
without creating pointless profiles for every host.

### A username-only profile counts as stored credentials

The pure coverage function treats any live profile as credential-bearing
because it does not consult Keychain. A profile can contain only a username and
no key or password, yet it closes the `noStoredCredentials` gap.

### Never-connected hosts are not surfaced

Stale detection deliberately excludes hosts with no history. That distinction
is technically correct—unknown is not the same as stale—but the product has no
"Never connected" finding. For a newly imported 900-host fleet, that is likely
the most valuable category.

New 0.16 aggregate history also starts empty, so the stale-host feature takes
months to become useful unless legacy recents are migrated or "never seen" is
shown separately.

### Recommended coverage model

Separate objective facts from optional organizational policies.

Objective facts:

- no environment tag
- never attempted
- never connected successfully
- stale successful connection
- repeated connection failures
- dangling credential-profile reference
- unknown/missing SSH alias
- duplicate host/alias

Optional policies:

- must use a shared credential profile
- must be marked protected when environment is production
- must have an owner/team tag
- must have notes or a ticket/service identifier

Allow users to:

- enable the policies that apply to their fleet
- dismiss intentional exceptions
- filter by folder/environment/transport
- export findings
- jump directly to the host or select the affected hosts in the sidebar

## Architecture review

### Strengths

- System OpenSSH provides mature crypto, agent, host-key, ProxyJump, and config
  behavior instead of recreating a parallel SSH stack.
- Passwords are persistently stored in macOS Keychain.
- Askpass files are substantially hardened compared with a naive helper.
- Local-first JSON makes state inspectable and exportable.
- Pure models for panes, restore plans, coverage, ranking, and OSC parsing are
  easy to test.
- MultiExec has unusually explicit safety affordances.
- Protected-host behavior is treated as a first-class product concern.
- SFTP transfer cancellation reaches the child process.
- Remote-file editing handles atomic editor saves and retry behavior carefully.
- Sparkle uses a pinned EdDSA public key and release assets are notarized in the
  normal configured workflow.
- The app is small and genuinely native.

### Scaling concerns

The central files are becoming very large:

- `SessionManager.swift`: roughly 1,393 lines
- `SFTPPane.swift`: roughly 1,033 lines
- `HostOutlineView.swift`: roughly 760 lines
- `SessionStore.swift`: roughly 731 lines
- `SessionArea.swift`: roughly 713 lines

`SessionManager` currently coordinates:

- process creation
- direct serial/telnet transports
- credentials
- logging
- command history
- tabs
- pane trees
- restore
- MultiExec
- keyboard/mouse monitors
- SFTP selection
- workspace persistence

This concentration explains why apparently small features can create
cross-cutting regressions. After 0.16, a consolidation release should extract:

- `TransportFactory`
- `CredentialResolver`
- `SessionRecorder`
- `WorkspaceController`
- `BroadcastController`
- `TabHistory`

The goal is not abstraction for its own sake; it is to make lifecycle and
privacy policies testable without launching SwiftUI.

## Competitive benchmark

### MobaXterm

Official current material presents:

- Windows-only all-in-one remote toolbox
- SSH, mosh, telnet, serial, RDP, VNC, X11, SFTP, and more
- graphical SFTP browser and remote editor
- MultiExec
- macros
- password management
- jump hosts and tunnel UI

Recent 2026 releases added strong paste-safety features, including warnings for
homographs, zero-width characters, pipe-to-shell patterns, dangerous profile
redirects, and extraction-to-root patterns.

**Portside opportunity:** be the direct native-Mac migration target, not a
protocol-for-protocol clone.

Sources:

- https://mobaxterm.mobatek.net/
- https://mobaxterm.mobatek.net/features.html
- https://mobaxterm.mobatek.net/download-home-edition.html

### Tabby

Tabby is the closest open-source comparison:

- free and cross-platform
- SSH/SFTP, serial, telnet
- nested panes and restoration
- simultaneous multi-pane input
- integrated encrypted secrets
- jump hosts, X11, port forwarding
- plugins, themes, and customizable shortcuts
- careful multiline-paste behavior

Portside cannot rely on general feature bundling as its moat because Tabby
already covers much of it.

**Portside advantages:** native footprint, system OpenSSH compatibility,
MobaXterm import, protected-host semantics, first-class containers/Kubernetes,
and fleet governance.

Sources:

- https://tabby.sh/
- https://tabby.sh/about/features

### Termius

Termius leads on:

- polish across desktop and mobile
- cloud synchronization
- shared/team vaults
- collaboration and access control
- snippets and multi-execution

Current published pricing is free for the local starter tier, approximately
$10/month annually for Pro, $20/user/month for Team, and $30/user/month for
Business.

**Portside advantages:** no account, local ownership, open source, no
subscription, system OpenSSH, and a Mac-specific operations workflow.

Sources:

- https://www.termius.com/
- https://www.termius.com/pricing

### Royal TSX

Royal TSX offers:

- SSH/telnet, RDP, VNC, web, SFTP/SCP, and other management surfaces
- reusable and inherited credentials
- safe separation of connection documents and personal credentials
- command/key-sequence tasks
- dynamic folders and dynamic credential sources
- team-oriented document sharing
- €49 single-user license, with a limited free tier

**Portside opportunity:** dynamic inventory sources are a particularly valuable
idea to borrow without adopting Royal TSX's full remote-management breadth.

Source:

- https://www.royalapps.com/ts/mac/features

### SecureCRT

SecureCRT is the mature professional benchmark:

- Windows, macOS, and Linux
- rich terminal emulation
- session manager designed for one or thousands of sessions
- tab groups, snapshots, commands, and scripting
- reusable credentials
- tunnels and file-transfer integration

Current published SecureCRT pricing is approximately $119 for a single license

**Portside advantages:** modern native UX, open source, local inspectable data,
and stronger opinionated fleet safety.

Sources:

### iTerm2

iTerm2 already provides:

- tagged and searchable profiles
- shell-reported command history and exit status
- directory frecency
- keychain password manager
- automatic profile switching
- shell-assisted file upload/download
- deep terminal compatibility and automation

Therefore command history and frecency are useful parity features, not durable
differentiators by themselves.

Sources:

- https://iterm2.com/features.html
- https://iterm2.com/documentation-shell-integration.html

### WezTerm

WezTerm leads on:

- cross-platform terminal fidelity
- scripting/configuration
- workspaces and multiplexer domains
- native SSH tabs
- local and remote persistence
- graphics protocols, ligatures, and rendering depth

Portside should not try to beat WezTerm on terminal-emulation breadth. It should
continue treating SwiftTerm limitations honestly and win at operator workflow.

Sources:

- https://wezterm.org/features.html
- https://wezterm.org/ssh.html

### Wave Terminal

Wave is moving toward:

- visual workspaces
- embedded editor and file previews
- SSH connections
- remote files
- web and AI widgets
- local-first open-source positioning

It validates the broader "terminal as workbench" thesis but targets a graphical
and AI-oriented developer workspace more than guarded fleet operations.

## Recommended product direction

### Protect the narrow, differentiated center

Prioritize:

- large-fleet inventory and policy visibility
- safe MultiExec
- MobaXterm migration
- real OpenSSH compatibility
- container/Kubernetes operator flows
- local ownership and inspectability
- high-confidence remote-file workflows

Avoid chasing:

- RDP/VNC/X11 protocol count
- cloud synchronization
- team SaaS
- a custom SSH implementation
- terminal-emulation parity with iTerm2, WezTerm, or Ghostty

### Highest-value opportunities after 0.16

1. **Paste safety**
   - multiline confirmation
   - preview/edit before sending
   - invisible and suspicious Unicode detection
   - stronger confirmation in MultiExec and protected hosts

2. **Dynamic inventory**
   - CSV
   - Ansible inventory
   - command-backed/dynamic folders
   - Kubernetes contexts
   - `~/.ssh/config` as a continuously reconciled source rather than a one-time
     import

3. **Fleet policy**
   - configurable rules
   - dismissible exceptions
   - successful/failed connection health
   - duplicate and unreachable-host discovery

4. **Credential hardening**
   - Touch ID gating
   - a single credential-resolution path
   - optional external secret references later

5. **Durable remote sessions**
   - tmux control mode remains a strategically better fit than building a
     proprietary persistence layer.

### Recommended sequencing

1. Fix release blockers and add migration/release preflight tests.
2. Finish or narrow the promised 0.16 scope.
3. Run a real-host validation matrix:
   - successful SSH
   - rejected password
   - changed host key
   - timeout/unreachable
   - credential-profile tunnel
   - live SFTP download/edit/upload/cancel
   - mosh bootstrap
   - protected-host recording exclusion
4. Decide Intel/universal support explicitly.
5. Update changelog, README, website, compatibility matrix, and security policy.
6. Cut the release only from a clean, pushed commit with a fail-closed release
   script.
7. Follow 0.16 with a reliability/consolidation release before adding another
   large feature family.

feature velocity has outpaced lifecycle, migration, and release-integrity

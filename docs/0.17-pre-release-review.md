# Portside 0.17 pre-release review

Date: 2026-07-27  
Branch: `feature/polish-and-appearance`  
Reviewed head: `3f74a66`  
Base: `v0.16.0` / `79ab7a6`

## Verdict

**Hold the 0.17 release for one byte-stream fix.**

The branch is otherwise in strong shape. The additive appearance setting
decodes old and future data tolerantly, the real-library upgrade rehearsal
passes, recently closed tabs remain in memory, and the new coverage axis is
reported without making 100% coverage unreachable.

One defect in `SixelStreamGuard` can desynchronize it from SwiftTerm's DCS
parser. A remote process can make Portside insert a byte into ordinary terminal
output after a standards-defined DCS cancellation. This is not the original
fatal Sixel crash and I found no code-execution path, but a byte rewriter on
untrusted terminal output must not silently change bytes outside the exact
workaround case.

## Findings

### P1 — `SixelStreamGuard` does not honor DCS cancellation

**Location:** `Sources/Portside/Services/SixelStreamGuard.swift:107-148`

SwiftTerm treats CAN (`0x18`) and SUB (`0x1A`) as global cancellation controls
from every parser state. It also treats ST (`0x9C`) as a terminator before a DCS
handler has been selected. The guard handles none of those exits while it is in
`dcsPrologue`, and handles CAN/SUB as ordinary bytes while in `sixelBody`.

That leaves the guard in a different state from the terminal. A later ordinary
`q`, pixel-range text, and `ESC \` can then look like a Sixel payload to the
guard, which inserts `-` into output SwiftTerm is treating as normal text.

Minimal reproducer:

```text
input:  1B 50 18 71 7E 7E 1B 5C
        ESC P CAN q  ~  ~  ESC \

output: 1B 50 18 71 7E 7E 2D 1B 5C
                              ^^ inserted "-"
```

I verified this with a temporary regression test against the branch. The test
failed byte-for-byte:

```text
[27, 80, 24, 113, 126, 126, 45, 27, 92]
was not equal to
[27, 80, 24, 113, 126, 126, 27, 92]
```

The temporary probe was removed after verification; the worktree remained
clean apart from this report.

**Required fix**

- In `dcsPrologue`, reset to passthrough on CAN, SUB, and ST without injecting.
- In `sixelBody`, reset on CAN and SUB without injecting.
- Preserve the current behavior for ST terminating an actual Sixel body: inject
  only when the final band contains pixels.
- Add byte-exact tests for cancellation both before the DCS final byte and
  inside the Sixel body.
- Run each cancellation vector at every chunk boundary, as the existing positive
  Sixel cases do.

It would be safer to model the subset of SwiftTerm's transition table explicitly
instead of treating every unrecognized byte as “remain in the current state.”
The guard only needs a small subset, but its cancellation and final-byte rules
must stay synchronized with the parser it protects.

#### 8-bit DCS was investigated and is not a blocker at this pin

The guard does not recognize the 8-bit DCS opener (`0x90`). SwiftTerm's
transition table contains an 8-bit DCS transition, so this initially looked like
another way around the crash protection.

An executable probe against pinned SwiftTerm 1.15.0 showed that its ground-state
fast path consumes the 8-bit form as printable data; no Sixel handler is
dispatched. Therefore `0x90 q ... 0x9C` cannot reach the vulnerable decoder in
the dependency Portside currently ships.

No guard change is required for this release on that basis. When SwiftTerm is
upgraded, delete the guard as planned rather than extending it for a parser that
already contains the upstream Sixel fix.

### P2 — Close-tab documentation contradicts the shipped shortcut

**Implementation:** `Sources/Portside/Models/KeyBindings.swift:204-212`  
**Stale text:** `Sources/Portside/Services/SessionManager.swift:1356-1360` and
`docs/polish-and-appearance-plan.md:173-179`

The implementation binds Close Tab to Command-W and intentionally lets the
stock Close Window command lose that shortcut. The plan still says Close Tab is
Option-Command-W and that Command-W remains Close Window. The `SessionManager`
comment repeats the stale claim.

This is not a runtime defect, but it can produce incorrect release notes and a
false manual-QA result. Choose the intended behavior and make all three places
agree before tagging. The current implementation and latest commit message
clearly indicate Command-W is the newer decision.

### P2 / known limitation — Settings advertises resizing that does not hold

**Location:** `Sources/Portside/Views/SettingsWindowSizer.swift:20-28,68-99`

The branch already documents this accurately: the resizable style is added, but
on the ordinary path a manual drag snaps back to the content's ideal height.
The window therefore presents a resize affordance that often does not work.

This need not block 0.17 if the release claim is only “settings tabs size to
their content and cap/scroll on small screens.” Do not claim general manual
resizing. If it cannot be fixed before release, consider removing the
`.resizable` affordance on the path where SwiftUI will immediately defeat it.

### P2 — Critical raw-versus-repaired routing has no integration assertion

**Location:** `Sources/Portside/Services/SessionManager.swift:30-52`

The implementation order is correct: the logger and command timeline receive
the raw slice, and only `super.dataReceived` receives the repaired stream. That
preserves transcript offsets.

The current tests exercise `SixelStreamGuard` directly but do not lock this
`LoggingTerminalView` routing contract. Because moving the filter a few lines
up would silently invalidate persisted transcript offsets, add a focused test
that proves:

1. the transcript/logger receives the original bytes;
2. the command timeline receives the original bytes; and
3. the terminal receives the repaired bytes.

This is test hardening rather than evidence of a current runtime bug.

## Areas reviewed with no release-blocking finding

### Appearance persistence

- `appAppearance` is additive and defaults to `followSystem`.
- Missing values from pre-0.17 libraries decode correctly.
- Unknown future enum values fall back without discarding the rest of
  `TerminalAppearance`.
- Theme application preserves app appearance rather than coupling terminal and
  app colors.
- “Follow system” correctly maps to `NSApp.appearance = nil`.

### Recently closed tabs

- The ring is a bounded in-memory value and is not added to workspace storage.
- Reopening removes the selected history item, preventing duplicate reopening.
- Custom titles are restored without pinning a live terminal title.
- Clear is exposed.

One small hardening opportunity: `ClosedTabRing(limit:)` is internal but accepts
a negative value, for which `record` would eventually call `removeFirst()` on
an empty array. A `precondition(limit >= 0)` would make the invariant explicit.
Production uses the default of ten, so this is not a release concern.

### Never-connected coverage

- Empty history stays “unknown” instead of marking the whole fleet unvisited.
- Hosts with recorded history are not double-counted as never connected.
- Never-connected and stale are reported but excluded from the coverage score.
- The UI explains that only Portside-recorded connections count.

### Compatibility correction

The Sixel, iTerm2, and Kitty protocol claims are now backed by executable tests
against a real SwiftTerm `Terminal`. The former compatibility matrix was indeed
stale.

## Validation performed

- `git diff --check main...HEAD`: clean.
- Full suite: **264 tests, 0 failures, 4 skips**.
- Real-library upgrade rehearsal using
  `~/Library/Application Support/Portside/portside.json`: **passed**; the test
  operates on a temporary copy.
- Pinned SwiftTerm 1.15.0 was inspected at its actual parser and
  `SixelDcsHandler` implementation.
- Temporary executable probes:
  - DCS cancellation desynchronization: reproduced.
  - 8-bit DCS dispatch: not dispatched by the pinned parser, so the suspected
    bypass was disproved.

The full build also emits three existing test-code warnings (actor isolation,
`Thread.sleep` in an async context, and one unused binding). They are not caused
by this branch, but two become errors under Swift 6 language mode and are worth
putting on the maintenance list.

## Recommended release gate

1. Fix and regression-test CAN/SUB/ST state exits in `SixelStreamGuard`.
2. Re-run all 264 tests and the real-library upgrade rehearsal.
3. Reconcile the Command-W documentation.
4. Perform the pending runtime pass for Sidebar “New Local Shell,” settings tab
   sizing on a short screen, and recently closed tabs.
5. Ship 0.17; defer the settings manual-resize limitation only with release
   wording that does not promise it.
